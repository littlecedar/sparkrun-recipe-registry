**Which candidate this session would pick.** Take **(c)** now, before any answer: it costs a placement
rule and removes the exposure that killed the monitor twice. Then take **(a)**, but raise the swap
minimum to the top of its range (`-s 100,100`) rather than 90: both tests are "below minimum" conjuncts,
so a swap threshold near 100 collapses the AND onto the memory term, while a `-s 90` term only becomes
true after the engine has already pushed roughly 5 GiB into swap — measured, swap-free crossed 90 %
between 11:27:06 and 11:27:09, which is where `-m 14,5 -s 90,80` would have fired (47 s ahead of the
kernel, against 53 s for the memory term alone at `-m 30`), and it re-arms the same trap on a node whose
swap is untouched (`.34` idled at 99.98 % swap-free, where a `-s 90` term is unreachable).
`-m 30,15 -s 100,100` = 36.5 GiB sits 4 GiB below the 40.8 GiB spare the failed boot's own plan declared,
so a boot that obeys its plan does not trip it, and the pair is dry-run verified silent at idle and firing
when memory alone is low. Take **(b)** regardless of which memory threshold the owner picks: an adjacency
adjustment is the only thing the kernel honours, `--avoid` is not, and the master `sshd` already runs at
`-1000` while `ssh.service` itself declares `OOMScoreAdjust=0`.
