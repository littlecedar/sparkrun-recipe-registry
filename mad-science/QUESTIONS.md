The kernel picked host services because unified-memory GPU allocations are not in RSS: its victim table lists the engine as `sglang::schedul … 75356775` total_vm with `28169` kB rss and `oom_score_adj 0`, so engine badness is ≈0, the same as `ssh`. | `/etc/default/earlyoom:11`; `journalctl -u earlyoom` 11:27:03–11:27:57 and `dmesg -T` 11:27:55–57 on the head; `docker inspect` of the surviving `.30` container: `Memory=0 MemorySwap=0 OomScoreAdj=0`; mechanism and its falsification in `tools/README.md` §"run-arm.sh pooling receipts" | 2026-11-08 |

**Which candidate this session would pick.** Take **(a)**, but raise the swap minimum to the top of its range (`-s 100,100`) rather than 90: both tests are
"below minimum" conjuncts, so a swap threshold near 100 collapses the AND onto the memory term, while a `-s 90` term only becomes true after the engine has
already pushed roughly 5 GiB into swap — measured, swap-free crossed 90 % between 11:27:06 and 11:27:09, which is where `-m 14,5 -s 90,80` would have
fired (47 s ahead of the kernel, against 53 s for the memory term alone at `-m 30`), and it re-arms the same trap on a node whose swap is untouched
(`.34` idled at 99.98 % swap-free, where a `-s 90` term is unreachable). `-m 30,15 -s 100,100` = 36.5 GiB sits 4 GiB below the 40.8 GiB spare the failed
boot's own plan declared, so a boot that obeys its plan does not trip it, and the pair is dry-run verified silent at idle and firing when memory alone is
low. Take **(b)** regardless of which memory threshold the owner picks: an adjacency adjustment is the only thing the kernel honours, `--avoid` is not,
and the master `sshd` already runs at `-1000` while `ssh.service` itself declares `OOMScoreAdjust=0`.
