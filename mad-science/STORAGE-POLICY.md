## 1. What the runtime cache is, and how sparkrun prunes it

`${WOPR_USER_CACHE}/sparkrun/runtime-cache/` (i.e. `$HOME/.cache/sparkrun/runtime-cache/` on each
node) holds compiled/autotuned artifacts — torch.compile, Inductor, Triton, FlashInfer, TRT-LLM
autotuner — so a relaunch skips minutes of recompilation. The leaf is **not** a model name; sparkrun
derives it (`sparkrun/core/runtime_cache.py`, installed 0.4.0-alpha+gcd21f80):

```
leaf = <root>/<family>/[<image_key>/]<model_key>
model_key = sanitize_key_component(model)[:48] + "-" + sha256("<model>@<model_revision>")[:8]
```

`model_key` is `core/runtime_cache.py:193-205` and `sanitize_key_component` is `:162-180`
(`/`→`__`, everything outside `[A-Za-z0-9._-]`→`-`, runs collapsed, ends stripped, **truncated to 48
chars**, stripped again); `build_runtime_cache_mounts` assembles the leaf at `:373-401`. Because the
suffix folds in the pinned revision, **the 8-hex suffix is the identity**. `key_by_image` is off for
every runtime we ship except TRT-LLM, so our leaves are two deep: `<family>/<model_key>`.

### There is a prune path, and it is two paths

| path | when | what it will remove |
|---|---|---|
| launch-time sibling sweep | every launch | siblings of *this* launch's leaf, under the same family, whose `.sparkrun-last-used` marker is older than `runtime_cache.prune.max_age_days` (default **30**) |
| `sparkrun setup prune-runtime-cache` | manually | every runtime family under the root, `-mindepth 2 -maxdepth 3`, same marker test; `--older-than N`, `--all` (ignore the cutoff), `--dry-run` (report per-tree sizes, remove nothing) |

VERIFIED by running it, not by reading it. `sparkrun setup prune-runtime-cache --help` on the head
(2026-10-15):

> `'sparkrun run' already sweeps the trees it can see on every launch (disable with`
> `'runtime_cache.prune.enabled: false').  This is the manual sweep, for reclaiming space without`
> `launching something — and the only way to clear trees for a model or image you no longer run at all.`

Both paths age by the **marker file, never by directory mtime** (`core/runtime_cache.py:88-92`: a warm
tree that is only read never looks different to mtime), and both are generated by
`orchestration/runtime_cache.py:45-99` (`_prune_stanza`, which refuses any root shallower than
`_MIN_PRUNE_DEPTH` = 3 segments). Two consequences worth knowing before you rely on them:

- **A tree with no marker is invisible to both sweeps.** `[ -f "$_marker" ] || continue` — so
  "sparkrun will get round to it" is false for anything sparkrun did not stamp.
- **Nothing is pinned in this cache.** `sparkrun model-cache pin` protects the *manifest artifact*
  cache (`sparkrun model-cache list|inspect|prune|pin|…`), a different tree; the runtime cache has no
  pin concept, only the marker and `prune_max_age_days`.

Demonstrations, in order of cost:

```sh
# 1. the age cutoff really is 30 days: nothing on the head is that old
sparkrun setup prune-runtime-cache --hosts <head> --dry-run          # -> "Nothing to prune."
# 2. the full inventory, sizes, nothing removed
sparkrun setup prune-runtime-cache --hosts .30,.31,.32,.33,.34,.35 --all --dry-run
#    -> "Would remove 98 tree(s), 2550.4 GB."   (receipt: .scratch/storage/prune-dryrun-all-20261015.txt)
```

That recomputation is now a tool, so it is not re-derived by hand next time:

```sh

uv run python -B tools/cache-audit.py --census .scratch/storage/prune-dryrun-all-20261015.txt \
```

**Unit note.** Two scales meet in these tables, and they are not interchangeable:

- The runtime-cache and reclaim figures are `du -sk` / sparkrun's own receipt: **binary** units wearing
  the label those tools print (`du -sh` and the receipt both divide by 1024³ and say `GB`), so
  "94.8 GB" above is 94.8 GiB and is the same figure, byte for byte, as the receipt it came from.
- The HF-cache figures come from `hf cache ls`, which is **decimal**: verified 2026-10-15 on `.31`,
  `models--jzinno--Ornith-1.5-35B-A3B-DFlash2` measures 1 053 161 310 logical bytes and `hf cache ls`
  prints `1.1G` for it (1.053 GB decimal / 0.98 GiB). So the HF column overstates the same disk by ~7 %
  relative to the runtime-cache column.

Neither changes a budget judgement here, but a reader comparing an HF-cache figure against a Hub page
(different again) or against a `du` figure must not do it silently — and the `.scratch/storage/`
receipts preserve each number in the unit its own tool printed.

### The position

1. **Keep using the runtime cache.** It is a cache, so every tree is disposable, but the sweep only
   reaches marked, 30-day-old trees, and a cold rebuild of a 100 GB lobe costs real minutes. Deleting
   live trees to save disk on nodes with 1.4–2.6 TB free buys nothing.
2. **Triage by leaf key, not by name and not by `modlogs/`.** Recompute `model_key` from the recipes
   (`tools/cache-audit.py`) and treat a key no shipped recipe and no `attic/` arm produces as stale
   material. Keep the AGENTS.md marker rule as the recency gate on top of that, never instead of it.
3. **The two DS4 leftovers are the reclaim set** (§2). Everything else keyed-large in the fleet maps
   to a shipped arm.
4. **Let the 30-day sweep do the small work.** The `retired` and long-idle trees below 1 GB each are
   exactly what `--older-than 30` is for; no manual step is needed and none is worth the risk.

## 3. Per-node cache budget, and what enforces it

### What the nodes actually hold (measured 2026-10-15)

| node | HF cache (logical) | runtime-cache | `/home` used | free |
|---|---:|---:|---:|---:|
| `.30` | 2.0 TB | 239.7 GB | 2.1–2.2 TB | 1.4 TB |
| `.31` | 787.2 GB | 194.3 GB | 997 GB | 2.6 TB |
| `.32` | 1.0 TB | 734.8 GB | 2.0 TB | 1.6 TB |
| `.33` | 974.0 GB | 732.1 GB | 2.0 TB | 1.6 TB |
| `.34` | 1.2 TB | 398.3 GB | 1.7 TB | 1.9 TB |
| `.35` | 1.3 TB | 300.1 GB | 1.8 TB | 1.8 TB |

HF-cache sizes are `hf cache ls` logical bytes and are **decimal** (see the unit note above), so the HF
column reads ~7 % high against the runtime-cache column.

**But do not assume a repo cited twice is stored once.** The 2026-10-14 census's method note says the
cache is a `hub/blobs/<sha>` store with `models--X/blobs/*` symlinks into it, which would make a
second repo holding the same blob free. Measured on `.35` 2026-10-15, that holds for some repos and
not others, and the difference is the whole reclaim figure:

- `models--Aleph-Alpha--Kolibri-1` — a symlink farm: `du -sh` **9.6 M** against a reported 78.9 G.
- `models--z-lab--Qwen3.8-27B-DFlash2` — **0 symlinks**, 6 regular files, `model.safetensors` a real
  3 848 817 896 B, and `du -sb` == `du -sbL`. A second repo with the same blob hash on the same node is
  a second full copy (different inode, different byte count).

So an `hf cache ls` size is real disk for one materialization and ~0 for the other. **Never infer free
space from a shared blob hash; measure the tree** (`du -sb` vs `du -sbL` on the repo dir, and compare
`stat %i` of a file in each).

`.31` is the useful calibration point: its `df` used (997 GiB) minus its two caches (≈ 733 GiB HF +
194 GiB runtime) leaves **~70 GiB** that is neither — OS, docker images, `~/.cache/runtime`, checkouts.
On `.35` that third term is several hundred GiB, because it also carries `~/dsv41-engram` (48 GB),
`~/ComfyUI/models` (35.8 GB) and accumulated benchmark receipts. **A node's non-cache footprint varies
with what lane last ran on it**, which is why the budget's hard floor is *free space* rather than a
tighter cap on either cache.

### The budget

> **Runtime cache ≤ 0.5 TB per node. HF cache ≤ 2.2 TB per node. `df /home` free ≥ 1.0 TB at all
> times, on every node.**

Derivation, from what the nodes hold rather than from a round number:

- A node is 3.7 TB of NVMe. Neither cache alone explains a node's usage: the non-cache term is ~70 GiB
  on `.31` and several hundred GiB on `.35` (engram tables, ComfyUI weights, receipts, docker images).
- The largest artifact a node can be asked to take is the ds4 official checkpoint, 510.3 GB, and the
  largest single compile lobe measured is 295.9 GB (`.33`). 510.3 + 295.9 + ~0.2 TB of transient
  staging/distribution overhead ⇒ a node that cannot show **≥ 1.0 TB free *before* the download**
  cannot be handed an arm without evicting something first. The 1.0 TB floor is therefore what covers
  both the download and that variable non-cache term at once, rather than a number picked to look round.
- 3.7 TB − 1.0 TB free − ~0.3 TB of non-cache use ⇒ **~2.4 TB of cache per node**, split 0.5 TB
  runtime-cache (it self-prunes at 30 days; the worst measured lobe is 295.9 GB, so 0.5 TB holds one
  lobe plus a season of small trees) and **2.2 TB HF cache** (the rounder half, since it is the half
  that grows by whole model repos).

The number is not arbitrary, and the fleet agrees with it: `.32`/`.33` are the only runtime-cache
breaches (734.8 / 732.1 GB), and reclaiming §2's two stale DS4 keys brings them to **497.9 / 495.2 GB**
— under the cap. `.30` is the only HF-cache node anywhere near its cap (2.0 TB of 2.2 TB), and it is
the head, which is also the distribution source.

### Enforcement — the mechanism this repo can actually hold

1. **The product does the runtime-cache half.** `runtime_cache.prune.enabled` (default true) plus
   `prune_max_age_days` (default 30) is already a per-launch budget floor for marked trees; the manual
   sweep is the out-of-band version. Nothing to build — but configure it deliberately: a lane that
   ships four arms of the same family should not rely on the default 30 days if 0.5 TB is the cap, and
   `sparkrun setup prune-runtime-cache --older-than 14` is the lever.
2. **Active-arm-only residency is a procedure, and this is it.** When a lane's arm is switched on a
   node, the arm that stops serving is reclaimed with
   `hf cache rm model/<org>/<name>` (never `rm -rf` a `models--*` directory — it orphans blobs) on the
   nodes that were serving it, and the switch is recorded in the lane doc with the reclaim. The arm
   that is *active* stays; a *shipped* arm whose weights are on no node is one `sparkrun run` away from
   being re-fetched, which is the intended cost. Two node-free exceptions: the head is the distribution
   source and legitimately holds more, and a lane whose next measurement is queued in the same window
   keeps its next arm.
3. **The check is `tools/cache-audit.py`, and `tests/test_cache_audit.py` keeps it honest.** The tool
   prints per-node totals against `--budget-gb`, flags over-budget nodes (exit 1), and prints the
   reclaim list keyed by provenance; the guard test pins the key derivation, the parser's two input
   shapes, the merge rule, and the 72 h in-use gate — so the policy's *mechanism* cannot rot silently
   even though the policy's *numbers* are dated statements.
4. **A budget without a census is a wish.** The census is two read-only commands (below); run them
   before and after any reclaim campaign, and keep both receipts in `.scratch/storage/`.

```sh
sparkrun setup prune-runtime-cache --hosts .30,.31,.32,.33,.34,.35 --all --dry-run   # runtime-cache
# per node: hf cache ls; df -h /home                                                  # HF cache + disk
uv run python -B tools/cache-audit.py --census <receipts…> --budget-gb 500           # verdicts
```

The caveat is not the licence, it is the extra terms the AEON-7 card attaches: a "User Responsibility &

changes (Apache-2.0 §4(b)), and (iii) decide whether to pass the acceptance clause down. That is an
owner call, not an engineering one.

### Recommendation: keep the full exports — a sidecar is not available

The register calls AEON and orcarouter "the natural sidecar candidates". **They are not graftable as
small sidecars, and the reason is measurable:** the three packs are three *different quantisations* of
the same base, so the bytes that would ride in a sidecar are essentially every quantised tensor.

| pack | quantiser (from its own shipped config) |
|---|---|
| RadixArk | **NVIDIA ModelOpt** 0.47.0.dev0, `MIXED_PRECISION` — `mlp.{gate,up,down}_proj` NVFP4 group 16, all attention/GDN projections **FP8**, `lm_head` NVFP4, `kv_cache_quant_algo: FP8`, `exclude_modules: [mtp*]` |
| AEON | **llm-compressor**, `targets: [Linear]`, `ignore: [lm_head, re:.*visual.*, re:.*conv1d.*, re:.*mtp.*]`, scheme **NVFP4** (uniform; `lm_head` left BF16) |
| orcarouter | **compressed-tensors**, mixed NVFP4 FFN + FP8 attention/GDN, static FP8 KV, BF16 MTP head |

No two of those three assign the same dtype to the same tensor, so a tensor-level graft over the
RadixArk base would carry the abliterated *and* the requantised tensors of every layer — i.e. the pack.
The one real sidecar in this family is already built and is not weights: the drowzeys cyber chat
template plus YaRN overlays (~KB) that `recipes/cybersec/mods/provide-uncensored-chat-template` splices
over the AEON body. Contrast the ds4 precedent that makes sidecars look cheap: there the stock pack and
the abliterated overlay are both **EXL3 mul1 K=5** on the same base, so the delta is 104 tensors and
682 MB over a 197 GB pack (`recipes/cybersec/mods/graft-dsv41-ablit-wo-b`) — a same-quantiser pairing.

- **RadixArk** — base, stays as the resident full export. Nothing to save.
- **orcarouter** — licence clear; **keep the full export.** A sidecar would save ~24.7 GB/node and
  cannot be built from anything on the Hub today without a new quantiser-matched delta export.
- **sakamakismile (AEON)** — licence permitted with the acceptance-clause caveat above; **keep the full
  export**, same reason. ~20.6 GB/node.

**Size saved: 0 GB.** Building a same-quantiser delta for either pack is a re-quantisation project
(export the abliteration delta in the target scheme, verify it serves), not a storage task; if the
owner wants the ~45 GB/node back on `.32`, that is the work item, and it needs a boot receipt to ship
(the ds4 graft mod took one).
